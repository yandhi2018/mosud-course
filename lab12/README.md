# lab12. Транзакции и конкурентный доступ

Вариант 4, общая практическая. Подготовка — lab12.sql, команды двух независимых окон — session_a.sql и session_b.sql. Эти два файла выполняются **блоками**, по меткам A1/B1/A2/B2, а не целиком: ожидание другого окна — часть эксперимента. `\gset` — команда psql; в DBeaver подставьте полученные product_id вручную. session_a сохраняет исходную inventory и восстанавливает её в конце. Резервная таблица относится к одному занятию; перед новым занятием сохраните актуальное состояние заново.

Автоматическое воспроизведение: `verify_transactions.py` использует libpq из установленного PostgreSQL (`D:/Programms1/PostgreSQL/bin/libpq.dll`), стандартную библиотеку Python и два соединения к localhost:5433. При другом расположении клиента измените путь. Запускайте только после lab12.sql; результаты сохранены в transactions.json. Каждый эксперимент сохраняет и в finally восстанавливает qty/version выбранных товаров, удаляет только свои помеченные движения.

Проверенные backend PID: **A=186, B=187**.

| Эксперимент | Изоляция | Наблюдение | Способ исправления / объяснение |
|---|---|---|---|
| Потерянное обновление | READ COMMITTED | A и B прочли 10, итог 9 вместо 8 | Атомарный UPDATE либо блокировка перед чтением |
| SELECT FOR UPDATE | READ COMMITTED | B ждал Lock/transactionid, после A прочёл 9, итог 8 | Второй читатель блокирует и перечитывает актуальную строку |
| Последняя единица | READ COMMITTED | Один UPDATE вернул 0, второй — 0 строк, остаток 0 | WHERE qty>0 и уменьшение внутри UPDATE |
| Неповторяемое чтение | READ COMMITTED | A увидел 10, после COMMIT B — 9 | Каждый оператор получает новый снимок |
| Повторное чтение | REPEATABLE READ | A увидел 10 и снова 10 | Один снимок на транзакцию |
| Фантом | READ COMMITTED | Повторный COUNT изменился 0→1 | Новый снимок видит вставку B |
| Взаимная блокировка | READ COMMITTED | SQLSTATE 40P01, жертвой выбран A | Блокировать товары в одном порядке; повторить транзакцию жертвы |
| Конкурентное изменение | SERIALIZABLE | SQLSTATE 40001, повтор B дал итог 8 | Повторить всю транзакцию с новым снимком |

Фактический deadlock: `Process 186 waits for ShareLock ... blocked by process 187; Process 187 ... blocked by process 186`. Кто станет жертвой, зависит от порядка исполнения. После всех опытов оба выбранных товара восстановлены: qty=10, version=0.

## Контрольные вопросы

1. PostgreSQL отображает READ UNCOMMITTED на READ COMMITTED: чужие незафиксированные версии не видимы.
2. Обычный SELECT читает снимок; FOR UPDATE дополнительно блокирует выбранную строку для конкурирующих изменений до завершения транзакции.
3. UPDATE qty=qty-1 выполняет изменение над актуальной версией после ожидания конкурента, а константа из раннего SELECT остаётся устаревшей и может затереть его результат.

## Запуск и состав

Подключение: `psql -h localhost -p 5433 -U student -d olist`. Схема olist должна быть загружена по №1. Запуск из этой папки: `psql -h localhost -p 5433 -U student -d olist -v ON_ERROR_STOP=1 -f lab12.sql`. Каждый файл запускайте в отдельном сеансе: временные таблицы принадлежат сеансу. ФИО и группу впишите в шапку SQL. `results.txt` содержит фактический вывод на ваших CSV.

## Выполнение в DBeaver

`lab12.sql` выполняется обычным SQL-скриптом. Для двухоконных экспериментов используйте `session_a_dbeaver.sql` и `session_b_dbeaver.sql`: они не содержат команд psql и автоматически выбирают product_id. Откройте два отдельных соединения к одной базе, выполните подготовку в каждом и убедитесь, что pg_backend_pid() различается. Затем выполняйте выделенные блоки в указанной последовательности; BEGIN/COMMIT оставьте под управлением самих блоков. Не запускайте файлы двух сеансов целиком. Все блоки одного сеанса должны оставаться в одном соединении, поскольку lab12_params — временная таблица.
