# lab03. Выборка, проекция, переименование и реляционная алгебра

Вариант 4: отношение `customers`, предикат
`state ∈ {SP,RJ,MG} AND city IS NOT NULL`,
проекция `customer_unique_id, city, state`.

## Реляционное выражение

```
π customer_unique_id, city, state (
    ρ (customer_city -> city, customer_state -> state) (
        σ (customer_state IN {'SP','RJ','MG'} AND customer_city IS NOT NULL) (
            olist.customers
        )
    )
)
```

σ отбирает клиентов из трёх штатов с непустым городом, ρ переименовывает
атрибуты `customer_city`/`customer_state` в `city`/`state` по требованию
варианта, π оставляет только три нужных атрибута.

## О дубликатах и эквивалентности

- Выборка σ(p1 AND p2)(R) эквивалентна последовательному применению
  σ(p1)(σ(p2)(R)) — порядок двух фильтров не влияет на итоговое множество
  кортежей: разность результатов (п.1) и (п.4) на реальных данных Olist
  дала 0 строк, что подтверждает эквивалентность.
- В математической модели проекция π устраняет повторяющиеся кортежи по
  определению (отношение — множество), а SQL `SELECT` по умолчанию не
  удаляет дубликаты: `customer_id` в `customers` уникален, но
  `customer_unique_id` — нет (один и тот же человек может иметь несколько
  `customer_id`: в Olist он выдаётся на каждый заказ), поэтому проекция на
  `(customer_unique_id, city, state)` порождает повторяющиеся строки. На
  данных Olist: без `DISTINCT` — 66 233 строки, с `DISTINCT` — 64 010 строк,
  то есть 2223 строки-дубликата (покупатели с несколькими заказами из одного
  города).
- Перенос проекции раньше по дереву запроса (п.5) не меняет итоговый
  результат, но уменьшает число столбцов, которые нужно нести через
  промежуточные шаги — это иллюстрирует идею push-down проекции,
  используемую при оптимизации запросов.
